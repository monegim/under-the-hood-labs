# Lab 19 — Concept: The Boot Chain Before systemd Ever Starts

## What's actually going on

Booting a Linux machine is a chain of distinct stages, each handing off to
the next, and each with its own way of failing. Firmware (BIOS or UEFI)
loads the boot loader - GRUB2, on most Linux distributions. GRUB reads its
configuration (`/boot/grub/grub.cfg`, generated by `update-grub`/
`grub-mkconfig` from `/etc/default/grub` and the scripts in `/etc/grub.d/`,
rather than hand-edited directly) to find a menu entry, then has to
literally locate and load two files named in that entry: a kernel image
(`linux /boot/vmlinuz-...`) and an initramfs (`initrd /boot/initrd.img-...`).
This lab's main incident lives entirely at this stage: if either file
listed in the entry doesn't exist, GRUB fails before the Linux kernel has
executed a single instruction - the classic symptom is an on-screen
`error: file '...' not found`, and either falling through to the next menu
entry or, if nothing else is available, dropping to a `grub rescue>`
prompt, which is GRUB's own minimal interactive shell, not Linux at all.

Assuming GRUB successfully loads both files, it hands control to the
kernel, which unpacks and executes the initramfs - a small temporary root
filesystem (packed as a compressed cpio archive, inspectable with
`lsinitramfs`) whose entire job is finding and mounting the *real* root
filesystem before normal boot can continue. This is where Challenge A's
bug lives: the kernel and initramfs loaded just fine, but the initramfs's
own scripts are told to look for a root filesystem by a UUID
(`root=UUID=...`, set on the kernel command line by the same GRUB entry)
that doesn't match any actual device. The result is a completely different
failure signature - not a GRUB-level "file not found," but a kernel-level
"I'm running, but I can't find the disk I'm supposed to boot from,"
typically `VFS: Unable to mount root fs on unknown-block(0,0)` or the
initramfs's own boot scripts giving up and dropping to a busybox
`(initramfs)` shell. The same class of bug can also be caused by a missing
kernel module in the initramfs (e.g. the storage or filesystem driver
needed to even see the root device) - the initramfs's module set is
normally computed automatically from the currently running system's
`lsmod`/`/etc/initramfs-tools/modules`, and only goes stale if that
detection was bypassed or the initramfs was built for different hardware
than it's booted on.

The third piece - GRUB's *default entry selection* - is its own separate
mechanism worth understanding on its own, which is what Challenge B is
about. Ubuntu's GRUB is normally configured with `GRUB_DEFAULT=saved` in
`/etc/default/grub`, which tells GRUB to read which entry to boot from a
small persistent environment block (`grubenv`, typically
`/boot/grub/grubenv`) rather than always booting a fixed numeric index.
Two different commands write to that same block with very different
durability: `grub-set-default` writes a value that persists across every
future boot until explicitly changed again, while `grub-reboot` writes a
value that GRUB itself automatically clears the very next time it boots -
a true one-shot, regardless of whether that boot even succeeded. Mixing
these up - using `grub-set-default` when you meant "just try this once" -
is exactly how an unverified or broken entry becomes every future boot's
problem instead of just the next one.

## Where this shows up in the real world

Kernel upgrades are the single most common trigger for this entire class
of bug: a disk that fills up mid-`apt upgrade`, an interrupted package
install, or a manually-copied kernel image without a matching
`update-initramfs` run can all leave a kernel entry with no valid initrd
behind it - invisible until the next reboot selects that entry, which is
often much later (the next patch cycle, a host migration, an unplanned
power event) than whenever the actual mistake happened. Stale `root=`
UUIDs show up constantly in cloned VM images, disk-to-disk migrations, and
any workflow that swaps or re-partitions the underlying disk without
regenerating boot configuration from the new system's real state. And the
`grub-set-default` vs `grub-reboot` distinction matters most exactly when
you're testing something risky - a new kernel, a new initramfs, an
unverified config change - which is precisely when you want the "if this
doesn't come back up, the *next* reboot recovers automatically" guarantee
that only `grub-reboot` provides.

## Go deeper

- **Website/docs:** man7.org — https://man7.org/linux/man-pages/man7/boot.7.html
  — a concise overview of the full Linux boot sequence from firmware
  through init.
- **Website/docs:** Arch Linux Wiki — https://wiki.archlinux.org — has
  precise, thorough pages on GRUB configuration internals, initramfs/
  mkinitcpio mechanics, and recovering from a `grub rescue>` prompt; the
  best available explanation of this material outside the source code
  itself.
- **Website/docs:** GNU GRUB manual — https://www.gnu.org/software/grub/manual/grub/grub.html
  — canonical reference for `grub-mkconfig`, `grub-set-default`,
  `grub-reboot`, and the `grubenv` mechanism.
- **Book:** *The Linux Programming Interface* — Michael Kerrisk — covers
  the kernel/userspace boundary and early boot/init process lifecycle that
  the initramfs hands off into.
- **YouTube:** Learn Linux TV — https://www.youtube.com/@LearnLinuxTV —
  has dedicated boot-process, GRUB, and initramfs troubleshooting content.
