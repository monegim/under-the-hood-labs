# Lab 14 — Concept: Deleted-But-Open Files and Disk Space

## What's actually going on

On Linux (and Unix generally), a directory entry and an inode are two different things, and `rm`/`unlink()` only ever touches the first one. A directory is just a list of (filename → inode number) mappings. `unlink()` removes that mapping and decrements the inode's **link count**. The actual file data — the inode and the data blocks it points to — only gets freed when the link count hits zero **and** there are no open file descriptors referencing it. Every process that has the file open holds a reference into the kernel's open-file-description table, and that table entry pins the inode regardless of whether the file still has a name anywhere in the filesystem. This is why `rm`-ing a file a process is actively writing to doesn't free any space immediately: the name is gone, but the inode is still very much alive, and the process's fd still points straight at it.

This is exactly why `df` and `du` can disagree. `df` asks the filesystem how many blocks are actually allocated — it doesn't care whether those blocks have a name. `du` walks the directory tree summing up the sizes of files it can find by name. A deleted-but-open file has zero directory entries, so `du` can never see it, no matter how large it's grown, while `df` correctly reports the space as used. This isn't a bug in either tool; they're answering different questions ("what's allocated" vs "what's reachable by path"), and a deleted-open file is precisely the case where those two answers diverge.

`lsof +L1` finds these by looking for open files whose link count is under 1 — i.e., an inode with zero directory entries pointing to it but a nonzero open-reference count from `/proc/*/fd/*`. The `(deleted)` suffix you see in `lsof` output or in `readlink /proc/<pid>/fd/<N>` is not part of any real path — it's a cosmetic annotation the kernel appends purely for humans reading `ls`/`lsof` output, so trying to open that literal string will fail. The real handle is the fd itself, and you can act on it directly through `/proc/<pid>/fd/<N>`, which is a magic symlink the kernel resolves straight to the inode, bypassing the (now nonexistent) directory entry entirely. That's how `: > /proc/<pid>/fd/<N>` works as a fix: it's an `open()`-for-truncate on the underlying inode via that magic path, not a filesystem-path operation, so it reclaims the space without the process needing to close and reopen anything.

The forking case (Challenge B) is a different wrinkle on the same mechanism. `fork()` duplicates the parent's entire file descriptor table into the child, but each fd entry is really just a pointer to a shared kernel structure called the open file description (which tracks the file offset, access mode, etc.), which in turn points to the inode. After `fork()`, parent-fd-3 and child-fd-3 are two independent references into the *same* open file description/inode — closing one (including via the process dying) does nothing to the other's reference count. This is exactly the reference-counting model that makes "kill the process" an incomplete fix whenever there are other holders you haven't accounted for: the inode dies only when its link count is 0 **and** its open-reference count is 0, and there can be an arbitrary number of independent references from an arbitrary number of processes.

## Where this shows up in the real world

This is one of the most common "disk full but I can't find the big file" tickets an on-call engineer will ever see, almost always from a log rotation setup that deletes or renames a log file without telling the writing process to reopen it (`logrotate` without a working `postrotate`/`copytruncate`, or a homegrown `mv+rm` cron job with no `SIGHUP`/`kill -USR1` to the app). It also shows up with core dumps, temp files under heavy write load, and any prefork server (Apache `prefork`, PHP-FPM, Gunicorn, nginx workers) where a master opens a resource before forking — a restart of just the master leaves every worker's inherited fd holding the old inode open, silently defeating what looks like "we already restarted it." Knowing the inode-vs-directory-entry split turns a confusing symptom (df/du disagreement) into a five-minute diagnosis with `lsof +L1`, instead of a guess-and-restart-everything fire drill.

## Go deeper
- **Book:** *The Linux Programming Interface* — Michael Kerrisk. The authoritative reference on inodes, link counts, and how `open()`/`unlink()`/file descriptors actually interact at the syscall level — read the chapters on file I/O and links.
- **Book:** *Systems Performance* — Brendan Gregg. General methodology for diagnosing "where did my disk/resources go" problems, including file descriptor and disk usage analysis.
- **Website/docs:** man7.org — https://man7.org/linux/man-pages/ — read `inode(7)`, `unlink(2)`, and `proc(5)` (specifically the `/proc/[pid]/fd/` section) for the exact semantics this lab depends on.
