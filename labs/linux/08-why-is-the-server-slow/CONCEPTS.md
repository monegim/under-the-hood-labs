# Lab 8 — Concept: Load Average, CPU Accounting, and Memory Pressure

## What's actually going on

Load average is the number everyone quotes and almost nobody has actually read the definition of. It comes from `/proc/loadavg`, and the kernel computes it as an exponentially-weighted moving average sampled roughly every 5 seconds, folding in a count of tasks in `TASK_RUNNING` state (actually running or waiting for a CPU) *plus* tasks in `TASK_UNINTERRUPTIBLE` (D-state, blocked on I/O). That second part surprises people: load average is not a pure CPU metric. A box with three processes stuck in D-state on a slow disk and zero CPU activity can show a load average of 3.00. This is exactly why this lab's opening gotcha matters — `1.00` only means "fully saturated" relative to `nproc`, and it can be driven up by I/O waits just as easily as by CPU-bound work, which is the seed of Challenge B.

The scheduler side: modern Linux uses CFS (Completely Fair Scheduler, being replaced by EEVDF in newer kernels) with one runqueue per CPU. Each runnable task accumulates `vruntime` (virtual runtime, scaled by priority/nice value), and the scheduler always picks the task with the lowest `vruntime` off the red-black tree backing the runqueue — the practical effect is that every task gets a proportionate share of CPU time over any given window, rather than the strict round-robin of older schedulers. `top`'s `%CPU` column isn't measured by watching the scheduler live; it's computed by sampling `/proc/[pid]/stat` fields 14 and 15 (`utime`, `stime` — time spent in user mode and kernel mode, in clock ticks) at two points and dividing the delta by the wall-clock interval and number of cores. That's why `report-generator.sh` (a `yes | > /dev/null` loop) pins one core at ~100%: `yes` is a pure user-mode spin with no syscalls to block on, so it never leaves `TASK_RUNNING` and CFS just keeps handing it its fair share of one CPU, forever.

Challenge A (six `yes` processes) is really about how CFS treats fairness across *processes*, not total demand. With 6 runnable CPU hogs on, say, a 2-core box, CFS doesn't let one process monopolize a core while the others starve — it time-slices all runnable tasks roughly evenly across the available cores, so you get 6 rows each showing something like `(100 × nproc / 6)`%, none of which look alarming individually. The load average and the aggregate CPU-seconds consumed are identical in principle to one 600%-hungry process; only the presentation changed. This is why the lesson is "sum by command," not "look at the top row" — `top`'s default sort optimizes for finding one outlier, and a swarm defeats that specifically.

Challenge B is a completely different mechanism hiding behind the same symptom. When a process keeps allocating memory it never frees (`bytearray(50MB)` in a loop), the kernel first eats into free memory, then reclaims reclaimable page cache (clean file-backed pages get dropped, since they can be re-read from disk), and once that's exhausted it turns to swap — writing anonymous (not file-backed) memory pages out to a swap device so it can hand the physical RAM to the requesting process. Swapping is not a background nicety; it is a synchronous stall on the process(es) that need memory, and any process that touches a page which was swapped out takes a hard page fault to bring it back in, which now costs a disk I/O instead of a memory access — five to six orders of magnitude slower. `vmstat`'s `si`/`so` columns (swap in / swap out, in KB/s) are the direct evidence, and its `b` column (processes in uninterruptible sleep, blocked on I/O — including page-in) climbs as more processes get stuck waiting on the swap device. This is the mechanism behind "everything on the box feels slow" with `top` showing nothing scary in `us`/`sy`: the bottleneck moved from the CPU scheduler to the memory reclaim/swap path, and `top`'s default view simply doesn't surface that unless you also look at the `%MEM`/`RES` columns or run `free -h` alongside it.

## Where this shows up in the real world

"The server is slow" tickets that turn out to be a forgotten cron job, a debug script someone left running, or a batch job that got kicked off twice are extremely common — and the fast path to diagnosing them is always the same discipline this lab drills: check `nproc` alongside load average before reacting to the number, sum CPU by command not by PID, and treat `free`/`vmstat` as mandatory checks alongside `top`, not optional ones. The memory-pressure-disguised-as-slow pattern is arguably the more expensive one in production, because engineers who only learned "check `top` for the CPU hog" burn hours convinced there's a phantom CPU problem while the real culprit is a memory leak quietly swapping the box to death — and by the time OOM kicks in (the OOM Killer lab's territory) or the box becomes unresponsive, the diagnosis window has closed. The USE method (Utilization, Saturation, Errors) exists precisely to force you to check every resource — CPU, memory, disk, network — systematically instead of anchoring on whichever one you checked first.
