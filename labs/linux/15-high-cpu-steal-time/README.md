# Lab 15 — High CPU Steal Time

## Objective
Learn to recognize CPU steal time (`%st` in `vmstat`/`top`, `%steal` in
`mpstat`) — the signature of a hypervisor not giving your VM's vCPUs the
time they're owed, usually because of a noisy neighbor on shared infra —
and tell it apart from ordinary high CPU caused by your own workload.

## A note on honesty before you start
Genuine steal time requires a real hypervisor actively starving your VM
because something ELSE on the same physical host is hogging cores. That's
not something we can reliably force from inside a single lab VM. This lab
is split into two honest, clearly-labeled parts:

1. A **live, real exercise**: you'll generate actual CPU load with
   `stress-ng` inside your own VM and watch `vmstat`/`mpstat`. This
   produces real, high `%us`/`%sy` — **not** `%st`, because this load is
   self-inflicted. This is the essential contrast case: what CPU pressure
   looks like when it's your own process's fault.
2. **Reference sample files** (`vmstat-steal-REFERENCE.log`,
   `mpstat-steal-REFERENCE.log`), written into `/var/tmp/lab27/` by
   `setup.sh`. These are illustrative text, based on the real pattern seen
   during genuine noisy-neighbor incidents on shared cloud infra — they
   are **not generated by running anything on your machine**. Treat them
   exactly like a paste of output someone hands you in an incident ticket:
   your job is to read and diagnose them, not to reproduce them live.

If your lab VM happens to sit on genuinely oversubscribed shared infra
(some budget cloud VPS providers), you may actually see nonzero `%st` in
Step 2 for real — if so, that's a bonus, not a requirement.

## Why this matters
Every hosting model that isn't bare metal (public cloud, most VPS
providers, oversold hypervisors) can produce steal time. Engineers who
haven't seen it before waste hours tuning application code, connection
pools, or MySQL configs when the bottleneck is invisible to the guest
entirely — it's happening one layer down, at the hypervisor's CPU
scheduler. Recognizing `%st` fast is the difference between a 10-minute
"move this VM" fix and a multi-day wild goose chase inside the app.

## Prerequisites
- Linux VM, `sudo` access
- `stress-ng`, `sysstat` (for `mpstat`) — installed by `setup.sh` if
  missing

Check first:
```bash
nproc
vmstat 1 1
which stress-ng mpstat
```

## Step 1 — Baseline
```bash
systemd-detect-virt || echo "not detected / bare metal"
vmstat 1 5
```
Note the `st` column (last column in classic `vmstat` output — some
`procps` versions add a `gu`/guest column after it). On a normal, healthy
VM this should be at or near `0` at idle.

## Step 2 — Build the "before" state (self-inflicted load, real & live)
```bash
chmod +x setup.sh
./setup.sh
```
This installs `stress-ng`/`sysstat` if needed, then runs a real 20-second
CPU stress test pinned to all your vCPUs while capturing `vmstat`/`mpstat`
output to `/var/tmp/lab27/vmstat-selfload.log` and
`/var/tmp/lab27/mpstat-selfload.log`.

## Step 3 — Read the self-load capture
```bash
cat /var/tmp/lab27/vmstat-selfload.log
cat /var/tmp/lab27/mpstat-selfload.log
```
> You should see `us` (user) and maybe `sy` (system) climb close to 100%
> combined across cores, while `st`/`%steal` stays at (or near) `0`. This
> is the CONTRAST case: high CPU that is 100% your own process's fault.
> `top` would show `stress-ng` itself as the hog here — the guest can
> fully explain where the CPU went.

## Step 4 — Read the reference steal-time samples
```bash
cat /var/tmp/lab27/vmstat-steal-REFERENCE.log
cat /var/tmp/lab27/mpstat-steal-REFERENCE.log
```
Remember: these two files are the illustrative reference samples from
`setup.sh`, not something you just generated. Read them like a ticket
paste. Compare against Step 3:
- `%st`/`st` is high (30-60%) even though `%usr`/`us` is comparatively
  modest.
- `%idle` is NOT near 100%, but nothing inside the guest (no runaway
  process, no `top` hog) explains where the missing CPU went — because it
  didn't go anywhere inside the guest. It was never given to the guest by
  the hypervisor in the first place.
- Per-core (`mpstat -P ALL`) the steal is often uneven — some vCPUs are
  starved harder than others, which is itself a clue about which physical
  cores your vCPUs landed on.

> Gotcha: don't confuse `%st` (steal, a hypervisor-level problem) with
> `%wa`/iowait (a storage-level problem). Both can coexist with "the VM
> feels slow but no process explains it," but the fix is completely
> different — steal means "get off this host/get a dedicated one," iowait
> means "check your disk."

## Step 5 — The actual fix
There is no in-guest command that fixes steal time — that's the whole
point. The fix lives at the infrastructure layer:
- Move the VM to a different, less oversubscribed host.
- Request a dedicated-core / dedicated-host instance type.
- If it's your own hypervisor (Proxmox/KVM/VMware), check what else is
  scheduled on that physical host and reduce oversubscription, or pin
  vCPUs to physical cores (CPU pinning).
- If it's cloud, this is a support ticket / instance resize, not a config
  change.

The common mistake: seeing high load and slow response times, and
spending hours tuning the app, database, or connection pool — when
`vmstat`'s `st` column would have told you in five seconds that the
problem isn't inside the guest at all.
