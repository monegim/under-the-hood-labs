# Lab 10 — Concept: Static Routing

## What's actually going on

Every packet the kernel needs to forward goes through a routing table lookup, and the algorithm is **longest prefix match**: given a destination IP, the kernel finds the most specific (longest netmask) route that covers it, not just any matching route. Internally, the Linux kernel stores this in a compressed trie (`fib_trie`, visible via `ip route show table all` or `/proc/net/fib_trie`), but conceptually it's the same lookup a router ASIC does in hardware — walk the table, find the tightest-fitting prefix, use its next-hop. A static route is nothing more than a manually inserted entry in this table: "packets for `10.0.2.0/24` go out toward `10.0.12.2`."

FRR's architecture matters here because it splits "what should be true" from "what the kernel actually does." `staticd` is the daemon that owns your typed static routes and holds them in FRR's RIB (Routing Information Base) — FRR's own internal view of routing state. `zebra` is the piece that reconciles every routing protocol daemon's RIB entries (staticd, ospfd, bgpd, etc.) into one selected best route per prefix, then pushes that down into the actual Linux kernel FIB via netlink. This is why `show ip route` in `vtysh` can show you FRR's view distinctly from `ip route show` at the Linux shell — they're usually in sync, but they're genuinely two different data structures maintained by two different pieces of software, one of which is a real router daemon and the other is the kernel itself.

Having a route in the table is a necessary condition for forwarding, not a sufficient one. Layer 3 routing tells you *which interface and next-hop IP* to send a packet to; getting the packet onto the wire still requires Layer 2 resolution — ARP, in this all-IPv4 lab — to turn that next-hop IP into a destination MAC address. This is exactly why Challenge B produced a route that "looks correct" (right prefix, present in `show ip route`) but is functionally dead: `10.0.12.99` was never a real address anyone answered ARP for, so the kernel has a route with no way to actually deliver to it. `ip neigh` showing `FAILED` or nothing at all is the tell — the routing table and the ARP/neighbor table are two separate pieces of state that both have to be correct.

Static routing is inherently per-direction and per-hop: nothing about configuring a route from A to B implies anything about the reverse path. Every router along the path needs its own route back toward the original source for a round-trip (ping, TCP handshake, anything) to complete — this is exactly the asymmetric-routing trap in Challenge A. r2 could forward the request just fine using its directly-connected route to `10.0.2.0/24`, and it wasn't until the *reply* needed a route back to `10.0.1.0/24` that the missing entry mattered. This is the single most common static-routing bug in production: someone adds a route on one router and forgets the router at the other end of the path needs the mirror-image entry.

## Where this shows up in the real world

- **Cloud VPC route tables** (AWS route tables, GCP routes, Azure route tables) are literally static routes: a prefix, a next-hop (internet gateway, NAT gateway, VPC peering connection, VPN gateway), evaluated by longest-prefix-match exactly like this lab's kernel FIB.
- Site-to-site VPN gateways and small branch offices almost always use static routes instead of a routing protocol — there's no need for automatic topology discovery when there's exactly one path and it rarely changes.
- **Diagnosis scenario:** "the VPN tunnel is up but only one side can reach the other" is Challenge A's exact symptom, wearing cloud-networking clothes — a missing return route in one VPC's route table (or one side of a VPN's static routes) while the tunnel/link status itself reports healthy. Knowing to check the *return* path's route table separately from the forward path's is what turns this into a five-minute fix instead of an escalation.
