# Lab 28 — Concept: File Descriptor Limits (and Why Two Layers Enforce Them)

## What's actually going on

Every process has a per-process resource limit on how many file descriptors it can hold open at once, tracked by the kernel as `RLIMIT_NOFILE`. It has a **soft** limit (the ceiling actually enforced right now, which a process can raise up to the hard limit itself) and a **hard** limit (the ceiling on the soft limit, which only a privileged process — `CAP_SYS_RESOURCE`, i.e. effectively root — can raise). These are read and set via the `getrlimit(2)`/`setrlimit(2)` syscalls, and `ulimit` in a shell is just a thin wrapper around the same syscalls for the shell's own process. When a process hits its soft `RLIMIT_NOFILE`, any further `open()` call fails with `EMFILE` ("too many open files") — that's a hard stop at the *process* level, completely independent of whether the *system* as a whole has plenty of file handles free.

The reason this incident class is so confusing in practice is that Linux has two entirely separate mechanisms for *setting* that per-process limit, and they don't know about each other. If a process is started by systemd, PID 1 forks and execs it directly — there's no login session anywhere in that path — so the limit comes exclusively from the unit's `LimitNOFILE=` directive (falling back to `DefaultLimitNOFILE=` in `/etc/systemd/system.conf` if unset). If a process is started via a login session instead — an SSH login, `su -`, sometimes cron depending on configuration — the limit comes from `pam_limits.so` reading `/etc/security/limits.conf` (and `/etc/security/limits.d/*.conf`) at session-start time. Editing `limits.conf` does nothing for a systemd-managed process, because `pam_limits.so` never runs in that startup path at all; conversely, editing a systemd unit's `LimitNOFILE=` does nothing for a process started from your shell. The mistake of raising the wrong one and being baffled when nothing changes isn't a config typo — it's a structural fact about *how the process was launched*, not what kind of workload it is.

There's a second, independent layer above both of these: the kernel's system-wide table of open file handles, governed by `fs.file-max` (visible via `cat /proc/sys/fs/file-max`) with current usage in `/proc/sys/fs/file-nr`. This ceiling applies across every process on the box combined. If that global table fills up, no amount of raising any single process's `RLIMIT_NOFILE` will help — you need `sysctl fs.file-max=<bigger>`. So a real `EMFILE`/"too many open files" incident actually has three places to check, not one: this process's soft limit (`/proc/<pid>/limits`), which mechanism set it (systemd unit vs PAM), and the system-wide ceiling (`fs.file-max`/`file-nr`) — and they require three different fixes.

Two more mechanics worth being precise about: `prlimit --pid <PID> --nofile=...` can change a *running* process's limits live via the same `setrlimit()` syscall, without a restart — this only affects new `open()` calls going forward, it doesn't retroactively un-fail whatever already failed. And systemd unit files are parsed into an in-memory model that `daemon-reload` is what actually refreshes — editing the file on disk changes nothing about what systemd currently believes the unit says until you tell it to re-read, which is why "I edited the file and restarted" can still silently run with stale limits.

## Where this shows up in the real world

This is a constant source of production incidents in any fleet with a mix of systemd-managed daemons and PAM-based login/cron setups, because the "obvious" fix (bump `limits.conf`, or bump the systemd unit, whichever you happen to think of first) is a coin flip that's wrong exactly half the time depending on how the process actually starts. It's also the reason database servers, load balancers, and anything holding thousands of concurrent connections ship explicit `LimitNOFILE=` overrides in their systemd units by default — the stock `1024` soft default from decades-old defaults is nowhere near enough for a modern connection-heavy service. Knowing to check `systemctl show <unit> -p LimitNOFILE` (not `ulimit -n` in your own shell, which tells you nothing about a different process) before touching any config file is what separates a two-command diagnosis from an hour of "I already fixed this, why is it still crashing."

## Go deeper
- **Book:** *The Linux Programming Interface* — Michael Kerrisk. Covers `getrlimit`/`setrlimit` and resource limits in depth — the definitive reference for exactly what `RLIMIT_NOFILE` means and how soft/hard limits interact.
- **Book:** *Systems Performance* — Brendan Gregg. Useful for the broader methodology of diagnosing resource-exhaustion incidents (file descriptors included) systematically rather than by guesswork.
- **Website/docs:** man7.org — https://man7.org/linux/man-pages/ — read `proc(5)` (for `/proc/[pid]/limits` and `/proc/sys/fs/file-max`), `getrlimit(2)`, and `limits.conf(5)` (the PAM config format).
- **Website/docs:** systemd's own documentation — https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html — the authoritative reference for `LimitNOFILE=` and the other `Limit*=` directives, and how they relate to `DefaultLimitNOFILE=` in `system.conf`.
