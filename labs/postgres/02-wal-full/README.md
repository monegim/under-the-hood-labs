# Lab 32 — An Inactive Replication Slot Fills the WAL Disk

## Objective
Watch `pg_wal` fill a bounded disk while write volume looks completely
normal, trace it to a replication slot that nothing has ever consumed
from, and learn to treat `pg_replication_slots` as a monitored resource,
not a "set it and forget it" object.

## Why this matters
A replication slot exists to guarantee the primary won't remove WAL (or,
for logical slots, catalog rows) that a replica/consumer still needs —
even across a restart of either side. That guarantee is exactly what
makes an abandoned slot dangerous: if the thing that was supposed to
consume from it disconnects, crashes, or was a one-off `pg_basebackup`
that never even started streaming, the slot keeps reserving WAL forever
by default. There is no size cap unless you explicitly set one. This
produces one of the most disruptive Postgres incidents there is — the
primary's disk filling from WAL alone, with the actual table data barely
growing — and the fix (drop or advance the slot) is trivial once you know
where to look, but invisible if you only ever watch table sizes or query
volume.

## Prerequisites
- Docker + the `docker compose` plugin
- `sudo` access on the host, plus `losetup`/`mkfs.ext4` (part of
  `util-linux`/`e2fsprogs`, present by default on most Linux hosts) — this
  lab needs a real, bounded filesystem to fill, the same trick used in
  `labs/linux/11-disk-full-writes-fail`.

Check first:
```bash
docker version
docker compose version
which losetup mkfs.ext4
```

## Step 1 — Bring up the incident
```bash
chmod +x setup.sh
./setup.sh
```
This script:
1. Creates a 300MB loop-mounted ext4 filesystem on the host and bind-mounts
   it into the primary as its WAL directory (`--waldir` at initdb time, so
   `PGDATA/pg_wal` is a symlink to it).
2. Starts the primary via `docker compose`.
3. Creates a `bloatme` table.
4. Creates a **physical replication slot** (`stuck_slot`) and never starts
   anything that streams from it — simulating a replica that was
   provisioned once (or a `pg_basebackup` that recorded a slot) and then
   never came back.
5. Runs a bounded (60-iteration) insert/delete workload against the table.
   This is expected to eventually fail with `No space left on device` once
   the WAL disk fills — that failure IS the incident, not a bug in the
   script.

## Step 2 — See the misleading signal
```bash
docker exec lab32-primary psql -U postgres -d appdb -c "SELECT count(*) FROM bloatme;"
docker exec lab32-primary psql -U postgres -d appdb -c \
  "SELECT pg_size_pretty(pg_total_relation_size('bloatme'));"
```
The table itself is tiny — rows get deleted every cycle. Nothing here
suggests a disk-full incident.

## Step 3 — Check the real signal
```bash
df -h ./data/wal-disk
```
> Gotcha: `pg_wal`'s disk usage climbing has nothing to do with the table
> data volume. WAL is generated by every write regardless of whether the
> table stays small, and normally old WAL segments get recycled once
> they're no longer needed for crash recovery or by any replication slot.

## Step 4 — Find what's pinning WAL
```bash
docker exec lab32-primary psql -U postgres -c \
  "SELECT slot_name, slot_type, active, restart_lsn, wal_status,
          pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
   FROM pg_replication_slots;"
```
`active` is `f` (false) — nothing is currently connected to this slot —
yet `restart_lsn` is frozen far behind the primary's current WAL position,
and `retained_wal` shows exactly how many bytes of WAL are being held back
because of it. `wal_status` (PG13+) tells you how dangerous this is:
`reserved` (still within normal retention), `extended` (beyond
`max_wal_size` but still protected), `unreserved` (about to be lost if WAL
generation continues), or `lost` (already gone — the slot is now unusable
without a fresh base backup).

## Step 5 — Fix it
Drop the slot that nothing is using:
```bash
docker exec lab32-primary psql -U postgres -c \
  "SELECT pg_drop_replication_slot('stuck_slot');"
docker exec lab32-primary psql -U postgres -c "CHECKPOINT;"
```
Then confirm the WAL disk is recovering:
```bash
df -h ./data/wal-disk
```
Old WAL segments that were only being retained for this slot become
eligible for recycling at the next checkpoint.

In production, before dropping a slot you don't recognize, always confirm
first whether anything is *supposed* to be consuming from it — dropping a
slot a real, temporarily-disconnected replica needs will force that
replica to re-sync from a fresh base backup once it reconnects and finds
its WAL gone.

## Challenges (don't read ahead — diagnose before you fix)

**Challenge A — a logical slot pins more than WAL:**
```bash
docker exec lab32-primary psql -U postgres -c "ALTER SYSTEM SET wal_level = logical;"
docker restart lab32-primary
# wait for it to become healthy again, then:
docker exec lab32-primary psql -U postgres -c \
  "SELECT pg_create_logical_replication_slot('stuck_logical_slot', 'test_decoding');"
```
Re-run the write workload from Step 1's loop. WAL grows the same way, but
this time check:
```bash
docker exec lab32-primary psql -U postgres -c \
  "SELECT slot_name, slot_type, active, catalog_xmin, restart_lsn FROM pg_replication_slots;"
```
A logical slot holds back more than WAL segments. Diagnose what else it's
protecting and why that's arguably worse for a busy cluster.

**Challenge B — the "safety net" that isn't free:**
```bash
docker exec lab32-primary psql -U postgres -c \
  "ALTER SYSTEM SET max_slot_wal_keep_size = '100MB'; SELECT pg_reload_conf();"
```
Re-create `stuck_slot` and re-run the write workload again. This time the
WAL disk does NOT fill up — but check the slot afterward:
```bash
docker exec lab32-primary psql -U postgres -c \
  "SELECT slot_name, active, restart_lsn, wal_status FROM pg_replication_slots;"
```
Something else has broken instead. What actually happened to the slot,
and what would happen to a real replica that was relying on it if it
reconnected right now?
