# Lab 19 — Solutions

## Challenge A — silent drop at the server's own firewall

**Check:**
```bash
docker exec clab-pcap-lab-client tcpdump -ni eth1 -c 6 tcp port 8080
```
The client sends a SYN, gets nothing back, and retransmits the same SYN
a few times with growing gaps (roughly 1s, 2s, 4s — Linux's default SYN
retry backoff), then gives up. No RST, no SYN-ACK, ever.
```bash
docker exec clab-pcap-lab-r1 tcpdump -ni eth2 -c 6 tcp port 8080
```
r1's server-facing interface shows the SYN (and each retransmit) being
forwarded through to the server just fine — r1 and the path up to the
server are innocent.
```bash
docker exec clab-pcap-lab-server tcpdump -ni eth1 -c 6 tcp port 8080
```
The SYNs *do* show up here too — they reach the server's NIC. But no
SYN-ACK ever goes back out.
```bash
docker exec clab-pcap-lab-server iptables -L INPUT -v -n
```
The DROP rule's packet counter is incrementing on every attempt.

**Diagnosis:** the packet makes it all the way to the server's network
interface — tcpdump proves that — but the server's own host firewall
discards it before it's ever handed to the listening socket. tcpdump
captures at a point in the kernel that's largely upstream of netfilter's
filtering decision, so "tcpdump saw it" and "the OS delivered it to the
application" are two different facts. The client's retransmit pattern (no
RST, no reply, exponential backoff) is exactly what a silent drop looks
like from the sender's side.

**Fix:**
```bash
docker exec clab-pcap-lab-server iptables -D INPUT -p tcp --dport 8080 -j DROP
```

**Lesson:** a packet showing up in a capture is not proof it reached the
application — always check the actual firewall ruleset and its hit
counters on the host in question, not just whether a tcpdump shows the
packet arriving.

## Challenge B — RST injected by a middlebox, not the destination

**Check:**
```bash
docker exec clab-pcap-lab-client tcpdump -ni eth1 -c 4 tcp port 8080
```
A SYN goes out, and almost immediately a `Flags [R.]` comes back — at
first glance identical to the "nothing listening" case from Step 4, source
IP `10.0.2.10` (the server).
```bash
docker exec clab-pcap-lab-server tcpdump -ni eth1 -c 4 tcp port 8080
```
Nothing arrives here at all — no SYN, nothing. The server never saw this
connection attempt.
```bash
docker exec clab-pcap-lab-r1 iptables -L FORWARD -v -n
```
The REJECT rule's counter is incrementing on r1.

**Diagnosis:** the RST the client received didn't come from the server —
it was generated by r1's `REJECT --reject-with tcp-reset` rule in its
`FORWARD` chain, which crafts a reset that looks like it came from the
original destination address. If you'd only captured on the client, you'd
have concluded "the server refused the connection" — exactly wrong. The
server-side capture showing absolutely nothing is the proof that something
mid-path is answering on the server's behalf.

**Fix:**
```bash
docker exec clab-pcap-lab-r1 iptables -D FORWARD -p tcp --dport 8080 -j REJECT --reject-with tcp-reset
```

**Lesson:** an immediate RST does not prove the destination host refused
the connection — it only proves *something* on the path said no. Only a
capture at more than one point (ideally including the actual destination)
can tell you whether that "no" came from the real endpoint or from a
device impersonating it along the way.
