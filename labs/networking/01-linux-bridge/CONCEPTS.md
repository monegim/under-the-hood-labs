# Lab 1 — Concept: Linux Bridge

## What's actually going on

A Linux bridge is a real, in-kernel L2 switch — not a metaphor for one. When you run `ip link add br0 type bridge`, the kernel creates a `net_device` of type bridge that other interfaces can be enslaved to. "Enslaving" a port (`ip link set veth1-br master br0`) registers an `rx_handler` on that interface: from that point on, every frame arriving on `veth1-br` gets intercepted before it reaches the normal IP stack and handed to the bridge's forwarding code instead (`br_handle_frame` in the kernel source). That's the fundamental trick — a bridge port isn't "connected to" an IP interface, it's grabbed at the device layer and switched purely on Ethernet headers, exactly like a real switch ASIC never looking at IP.

The forwarding decision itself comes from the FDB (forwarding database) — the exact functional equivalent of a switch's CAM table. It's a hash table keyed on MAC address, mapping each learned MAC to the port it was last seen arriving on, with an age timer (default 300s). This is what `bridge fdb show` prints. Learning is dead simple: on every incoming frame, the bridge records "this source MAC came in on this port." Forwarding is just a lookup: known destination MAC → send out that one port; unknown destination MAC → flood out every other port (this is why a brand-new bridge with no traffic yet floods everything — it hasn't learned anything). There's no coordination protocol needed for any of this; it's purely reactive to traffic you send.

The two failure modes you triggered in the challenges map to two genuinely separate pieces of kernel state. `master br0` sets a port's enslavement (visible in `bridge link show`); `ip link set ... up/down` sets the interface's administrative state (`IFF_UP`, visible in `ip link show`). A port can be enslaved and down at the same time — the bridge dutifully lists it as a member, but `rx_handler` never fires because the interface layer below it is dark. Then there's the bridge device's own state: `br0` itself is a `net_device` with its own up/down flag, and if it's down, the bridge's forwarding function is short-circuited entirely regardless of what any individual port reports — the "backplane" analogy in the lab is not just a teaching device, it's structurally accurate to how the kernel gates this.

`docker0` is this exact mechanism with automation on top. When Docker starts, it creates a bridge device (by default named `docker0`) the same way you did with `ip link add`, assigns it a private subnet and an IP as the gateway address, and enables `net.ipv4.ip_forward`. Every time you `docker run` a container on the default bridge network, Docker creates a veth pair, puts one end in the container's network namespace, and enslaves the other end to `docker0` — literally the same four commands you ran by hand in Steps 2-3. Kubernetes CNI bridge plugins (and the simpler configurations of Flannel/Calico) do the same thing per-node. Open vSwitch's kernel datapath is conceptually adjacent but mechanically different: instead of a single MAC-address FDB, OVS matches on arbitrary flow rules (a "flow table," not a CAM table) — same layer of the stack, different and more programmable data structure underneath.

## Where this shows up in the real world

- Every container platform's default networking (Docker bridge networks, most Kubernetes CNI plugins in non-overlay mode, Podman's default network) is a Linux bridge plus veth pairs, auto-wired instead of hand-wired.
- Hypervisor virtual switching (KVM/libvirt's default virtual networks, some OpenStack Neutron ML2 configurations) uses the same bridge device under a friendlier name like `virbr0`.
- **Diagnosis scenario:** two containers on the same Docker bridge network suddenly can't reach each other, but both have correct IPs and routes. Instead of guessing at iptables or DNS, `bridge link show` and `ip -d link show docker0` tell you in ten seconds whether a veth port got knocked down (common after a container restart races with a network reconfiguration) or the bridge itself is administratively down — the same two checks from this lab's challenges, just with Docker-managed names instead of hand-typed ones.
