# Lab 4 — Concept: NAT

## What's actually going on

NAT in Linux lives in netfilter's `nat` table, which is architecturally separate from the `filter` table you'll use in Lab 5 — this is why Challenge A's fix and diagnosis both point specifically at `iptables -t nat`, and why a backup/restore or config-sync tool that only handles the default filter table can wipe your NAT rules while leaving `FORWARD` looking completely untouched. The `nat` table only gets consulted for the **first packet of a new connection** (a `NEW` state in conntrack terms); every subsequent packet in that flow is handled by connection tracking instead, which is why a NAT setup, once established, doesn't re-run these rules per packet.

`MASQUERADE` and `SNAT` do the same fundamental thing — rewrite a packet's source IP as it leaves an interface — but `MASQUERADE` is specifically for interfaces whose IP can change (DHCP, dynamic cloud-assigned addresses): instead of a fixed IP baked into the rule, it looks up whatever address is currently assigned to the outbound interface at the moment each new connection starts. This is exactly what happens in Step 5 — `host-ext` sees the ping arriving from `203.0.113.1`, the router's own address on `eth2`, because MASQUERADE rewrote the source on the way out. Critically, this only works for packets actually egressing the named interface: this is the entire mechanism behind Challenge B. A `POSTROUTING -o eth1` rule only ever matches traffic leaving via `eth1` — traffic from `host-int` toward `host-ext` leaves via `eth2`, so that rule sits in the table syntactically valid and semantically useless, never incrementing its hit counter. A rule existing is not the same as a rule matching anything, and `iptables -L -v` (with counters) is the only way to tell the difference from a `-L` without them.

DNAT works in the opposite direction and at a different point in the packet's journey: it fires in `PREROUTING`, *before* the routing decision is made, rewriting the destination IP/port so that the kernel's subsequent route lookup happens against the *new* destination. This is why the DNAT rule in Step 6 (`--to-destination 192.168.100.10:8080`) makes the routing decision send the packet toward `host-int` even though it arrived addressed to the router's own external IP — by the time routing runs, the packet's destination has already been silently changed. Conntrack keeps a mapping of this translation, so when `host-int` replies, netfilter automatically un-translates it back to look like it came from `203.0.113.1:8080`, not `192.168.100.10:8080` — `host-ext` never has any idea a rewrite happened at all.

Both of these primitives require `net.ipv4.ip_forward=1` because NAT only matters for traffic passing *through* the router to a different host — a router with forwarding disabled would never see this traffic reach the nat table's `FORWARD`-adjacent hooks in the first place; it would just be dropped at the IP layer before NAT logic is ever consulted.

## Where this shows up in the real world

- `docker run -p 8080:80` generates almost exactly the DNAT rule from Step 6, automatically, targeting the container's veth-assigned IP instead of a manually typed one; Docker's outbound container traffic uses a MASQUERADE rule on `docker0` for the same reason as Step 5.
- AWS/GCP/Azure NAT gateways and every consumer router's port-forwarding page are this same MASQUERADE + DNAT pair, wrapped in a managed service or a web UI — "why can't containers reach the internet" and "why doesn't port forwarding work" both reduce to checking exactly these two things: is there a POSTROUTING rule bound to the *actual* egress interface, and does a PREROUTING DNAT rule's destination match a route that's actually reachable.
- **Diagnosis scenario:** a newly provisioned VM or container can reach the internet by IP but a "for a while" pattern of intermittent failures traces back to a NAT rule that's present but bound to the wrong interface (a templated Ansible/Terraform variable pointing at `$internal_if` instead of `$external_if`) — `iptables -t nat -L POSTROUTING -n -v` and checking for zero-hit counters is the fast path to that diagnosis, versus hours spent re-checking IP addressing that was never wrong.
